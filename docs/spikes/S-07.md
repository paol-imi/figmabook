# S-07 · Storybook render loop (Storybook 10.6, React + Vite)

> **Status:** done for the slice part of BUILD B-16 (2026-11-19). Storybook 11 beta, 8.6 and 9.1 are hardening (B-140, B-141) and not covered here.
> **Code:** `spikes/S-07/` (prototype channel driver, plans, runs, report renderer), `tools/sandboxes/` (sandbox generator).
> **Raw results:** `spikes/S-07/results.json` (one line per variant). Re-run with `pnpm build && pnpm -F @holotype/spikes s07`; print the tables below with `pnpm -F @holotype/spikes s07 report`. A 20-variant version runs as `pnpm -F @holotype/spikes test:e2e`.

## Headline

| Question | Answer (Storybook 10.6.7, Chromium 153, one page unless noted) |
| --- | --- |
| Channel vs URL throughput | **21–26 variants/s vs 4–5/s** on the 200-variant ds-react plan (4.2–6.3×); 4 pages in parallel: **50.5/s vs 8.6/s** |
| Per-variant latency (channel) | p50 **33–45 ms**, p95 **48–68 ms**; args-only update p50 41 ms, story switch p50 33–51 ms. URL: p50 191 ms, p95 246 ms |
| Where the channel time goes | Storybook steps p50 7 ms (p95 23); settle (`fonts.ready` + two rAF) p50 23 ms (p95 32); CDP round trips, `loadStory` and root handles p50 9 ms |

| Failure detection | Channel **20/20** injected faults reported with the right code; URL 16/20 (no stability check; cannot carry React-node args) |

| HMR / index change mid-run | CSS, component and CSF edits apply in place in ≈ 52 ms; a new CSF file renders through the channel ≈ 240 ms after the write, without a reload; an edit while a loader runs makes Storybook reload the preview, which the driver adopts and flags (`SB_HMR_DURING_CAPTURE`) |

Throughput figures vary by ±20 % between runs on this 4-vCPU container (three full runs: channel grouped 21.3–26.1/s, URL 4.1–5.5/s). Ratios are stable.

## Method

**Subjects.**

- `fixtures/ds-react` static build (B-03, Storybook 10.6.7, 52 stories after the `!figma` filter), served by `connectStorybook` (B-10).
- A generated sandbox, `react-vite@10.6` + the `faults` overlay (`tools/sandboxes`, 13 stories): built statically for failure injection, and run with `storybook dev` for the HMR run. Its pins equal the fixture's, so it installs from the local store in about 2 s.

**Environment.** Chromium launched as the capturer launches it (`channel: 'chromium'`, `CHROMIUM_ARGS`), browser contexts from `@holotype/capture` `contextOptions` (D-24: 1280×800, DPR 2, `reducedMotion`, user agent `… StorybookTestRunner holotype/<v>`, frozen `Date`, seeded `Math.random`). Every request outside 127.0.0.1 is aborted (none happened).

**Drivers.**

- *Channel*: the prototype in `spikes/S-07/driver/` (implements the B-10 `RenderDriver` contract). One page stays on `iframe.html`; each variant is one `page.evaluate` that drives the preview's channel and settles in the page (protocol below).
- *URL*: the B-10 driver, one navigation to `iframe.html?id=&args=&globals=` per variant.

**Plan.** `loadStory` metadata for every story (03 §4.1), then 200 variants: each story at its initial args, then single-arg changes (other enum options, boolean toggles, URL-safe text) and the dark theme global, round-robin by rank. *Grouped* order runs each story's variants back to back (what the capture pool does per `sid`); *interleaved* order switches story on every variant (worst case). Latency is the Node wall time of `driver.render()`, settle and root handles included; the first render of each page (the boot) is excluded from percentiles but included in throughput.

**Parity.** Every fifth variant (40) through the real capture pipeline (`createCapturer`, B-11: render, animation settle, serializer, 2× screenshot, canonical JSON, `captureHash`), once with the channel driver plugged in through `openDriver` and once with the URL driver, in plan order on one worker each.

**Failure injection.** 200 variants on the sandbox: healthy states of four stories with a fault every tenth position (8 kinds, 20 faults), render timeout 4 s. The variant after each fault is a recovery probe; its DOM signature (root `outerHTML` + every element's rect) is compared with the same variant rendered on a fresh page.

**HMR.** 60 healthy variants on the sandbox dev server; before variants 15, 30, 45, 52 the spike edits `button.css`, `Button.tsx`, adds `Added.stories.tsx`, edits `Button.stories.tsx` args; at 56 it edits `Probe.stories.tsx` 300 ms into a render whose loader takes 1.5 s. Edits are undone at the end.

Reading the numbers:

- **Renders per variant.** 1.36 in grouped order comes from the theme variants: setting `theme=dark` is one render, and the next variant pays a second render to reset it. With args presetting (Q8) a story switch costs one render; without it two (1.6 per variant interleaved).
- **Parallel pages.** 4 channel pages give 2.4× one page on 4 vCPUs; 4 URL pages give 1.7× (navigations contend for CPU). Capture-side work (serializer, screenshots) will lower both.
- **Capture cost.** In the parity run a full capture took 170 ms per variant through the channel and 232 ms through the URL path: once capture runs, the render is no longer the bottleneck, but the channel still saves ≈ 60 ms per variant.

## Storybook 10.6 quirks found

| # | Quirk | Consequence for the driver |
| --- | --- | --- |
| Q1 | **Args persist per story across `setCurrentStory`** in one page (the ArgsStore keeps them). 03 §5.3 resets `current.args` to `initialArgs` after a switch, which is wrong | Read the store (`storyStoreValue.args.get(id)`) or track `storyArgsUpdated`; never assume initial args after a switch |
| Q2 | `updateStoryArgs` with `undefined` **deletes** the key (`deleteUndefined`): the arg is then absent, not back at its initial value (`label: undefined` rendered an empty button) | Send the full set: `{...initialArgs, ...requested}`, `undefined` only for keys in neither (confirms the 03 §5.3 note) |
| Q3 | `updateStoryArgs` with unchanged args still re-renders | Compare before emitting; skip identical requests |
| Q4 | `storyFinished.status` is `"success"` for a story that threw and for a failed play function. Errors only show as `storyThrewException` / `playFunctionThrewException`, and the errored render still emits `storyRendered` + `storyFinished` ≈ 15 ms later | Errors win over the done event; after an error keep waiting (≤ 1 s) for that render's done event so it is not read as the next render's |
| Q5 | After a render error, re-rendering **the same story** through `updateStoryArgs` renders nothing and reports success; `<body>` keeps `sb-show-errordisplay` beside `sb-show-main`. `forceRemount` or a story switch recovers | Remount the next render of a story that errored; treat `sb-show-errordisplay` at the done event as "remount and retry" |
| Q6 | Tearing down a render still in `loading` (a story switch, or an HMR update of its CSF file) makes Storybook **reload the whole preview** (`location.reload`). The old execution context dies when the reload request starts, before the new document commits; a `page.goto` issued then is "interrupted by another navigation" or hangs. `updateStoryArgs` on a story stuck in `loading` only updates the store | After `SB_RENDER_TIMEOUT`, start the next render from a fresh navigation (≈ 300 ms) instead of switching. On a context loss, wait for a new document (new init-script id), adopt it after its boot render, then retry; never navigate over it |
| Q7 | Without the `StorybookTestRunner` user agent the `completing` phase waits ≈ 100 ms per render (animation wait); with it ≈ 0–2 ms | D-24 stays mandatory; check the UA in the adapter and warn when it is missing |
| Q8 | `loadStory()` initializes the ArgsStore entry of that story, so `updateStoryArgs` for a story that is not current succeeds (answered by `storyArgsUpdated` only, no render) | Preset the args, then `setCurrentStory`: one render per story switch instead of two |
| Q9 | On a top-level `iframe.html` the postMessage transport hands **every emitted event back** to the same window (static and dev). Storybook drops the echo before `channel.on` listeners; a recorder hooked on the transport sees each event twice | Record through `channel.on` or by wrapping `emit`, not the transport |
| Q10 | Dev server: file changes push `services:patches` and `storyIndexInvalidated`; a CSF or component edit makes Storybook re-render the current story by itself (`storyHotUpdated` → `storyPrepared` → `storyRendered` → `storyFinished`), twice for a new CSF file | A render in flight can receive an unsolicited done event: flag `SB_HMR_DURING_CAPTURE` when `storyHotUpdated` / `storyIndexInvalidated` arrive inside a render window and retry that variant |
| Q11 | Dev server: `index.json` lists a new CSF file ≈ 120 ms after the write, before the preview can import it: `loadStory` throws `importers[path] is not a function` for a short while | Map to `SB_STORY_LOAD_FAILED` and retry after the next `storyIndexInvalidated` |
| Q12 | Dev server: the first render of a CSF file takes up to ≈ 0.9 s (Vite on-demand transform) vs ≈ 45 ms warm | Keep `T.render` at 15 s on dev servers; optionally pre-warm with `loadStory` for every planned story (167 ms for 52 stories on static) |
| Q13 | `setCurrentStory` to an unknown id gives `storyMissing` plus a console error `SB_PREVIEW_API_0001 (MissingStoryAfterHmrError)` ("after HMR" even on a static build); the 03 §4.1 boot on `id=__holotype__` logs it too | Do not attribute console errors of the metadata boot to a story |
| Q14 | React 19 `useId` values (`_r_<n>_`) count mounts per page, so a warm page gives different `id` attributes than a fresh one | Capture must treat framework-generated ids as volatile (proposal P3) |
| Q15 | Live, non-serializable args work: a React element taken from another story's `initialArgs` passes through `updateStoryArgs` and renders. The URL path cannot carry it | Confirms the channel as the path for SLOT / INSTANCE_SWAP probes (03 §5.3) |
| Q16 | `__STORYBOOK_PREVIEW__.ready` exists and resolves at once after boot; `loadStory` per id works; `currentSelection`, `storyStoreValue.args`, `userGlobals.initialGlobals` exist. The 10.6 dev server serves `project.json` too (same capabilities as static) | 03 §3.1 / §4.1 "verify S-07" items confirmed for 10.6 |
| Q17 | 03 §5.5 step 8 (container rect + `body.innerHTML.length`) missed a root whose child width changes every frame: `#storybook-root` is a full-width block, and the markup length stays constant | Compare every element's rect under the root plus the root markup (the stricter check found 2/2) |
| Q18 | `updateGlobals` re-renders the current story; resetting a global is its own render | Order variants by globals, then component |
| Q19 | The seeded `Math.random` and frozen clock are init scripts, applied per document: in a warm page the random sequence continues across variants (no ds-react story uses it, so parity was unaffected) | Reseed before each render (proposal P2) |

## Channel driver protocol (spec for B-40)

The prototype that produced the numbers above (`spikes/S-07/driver/`):

1. **Page.** One page per worker; an init script records channel events with a sequence number and a per-document id. Boot by navigating to `iframe.html?id=<first story>&viewMode=story` (not `__holotype__`), wait for its done event, inject the fullscreen layout style once (toggle it per request for `keepLayout`).
2. **Per variant, one `page.evaluate`:** `ready()`; `loadStory(id)` for `initialArgs` (rehydrate `{$fromStory, arg}` markers here); desired = `{...initialArgs, ...args}`.
3. **Select** when the story is not current: if its store args differ, emit `updateStoryArgs` with the full set first (wait for `storyArgsUpdated`), then `setCurrentStory`.
4. **Args** when the current store args differ: one `updateStoryArgs` with the full set plus `undefined` for extra keys.
5. **Globals** when `{...initialGlobals, ...globals}` differs from `userGlobals.get()`: `updateGlobals`.
6. **Remount** when asked, and always when the done event finds `sb-show-errordisplay` on `<body>` (heal). Still there after the remount → `SB_STORY_ERROR`.
7. **Wait** for each step: arm before emitting; `storyMissing` → missing; the first error event wins, then wait ≤ 1 s for that render's done event; done = `storyFinished` (`storyRendered` without `caps.storyFinishedEvent`) for the story; deadline `T.render` across all steps.
8. **Settle:** `document.fonts.ready`, two rAF; the stricter stability check on the first render of each component.
9. **Node side:** a timeout makes the next render boot a fresh document; an "execution context destroyed" error means Storybook reloaded: adopt the new document (Q6), warn `SB_HMR_DURING_CAPTURE`, retry once; a document id that changed between renders warns the same and re-injects the layout.

## Recommendations for B-40

1. **Ship the channel loop as the primary path** with the protocol above; keep the B-10 URL driver as the fallback (`--no-channel`, no `__STORYBOOK_PREVIEW__`, a story that fails twice in the warm loop). It is 4–6× slower and cannot carry React nodes.
2. **Fix the 03 §5.3 algorithm**: read args from the store after a switch (Q1), skip unchanged requests (Q3), preset args before `setCurrentStory` (Q8), remount after an error on the same story (Q5).
3. **Replace "reload after two consecutive timeouts"** with "boot a fresh document after every timeout" (Q6): Storybook reloads itself anyway if you switch away, and the boot costs ≈ 300 ms. Keep the three-reload limit for `SB_STORY_UNRENDERABLE`.
4. **Handle self-reloads** by adopting the new document, never by navigating over it (Q6). The prototype's `adoptReload` is the reference.
5. **Waiter:** record via `channel.on` (Q9); errors win and swallow the errored render's done event (Q4); flag HMR events inside a render window (Q10) and retry the variant once, as 03 §9.2 says.
6. **Stability check:** use the stricter comparison (Q17) and update 03 §5.5 step 8.
7. **Types:** widen `RenderDriver.mode` to `'url' | 'channel'`, add `remount` to `RenderRequest` (03 §5.1 has it), add `SB_STORY_UNRENDERABLE` to `SbErrorCode`, and share the fullscreen CSS and root helpers between both drivers inside `packages/storybook`.
8. **Map `loadStory` failures** to `SB_STORY_LOAD_FAILED` (Q11), and warn (`SB_VERSION_UNTESTED`-style info) when the user agent lacks `StorybookTestRunner` (Q7).
9. **For the planner and pool (B-41+):** order variants by globals, then component (Q18); run one channel page per worker: 4 workers rendered 50 variants/s.
10. **Acceptance for B-40** can reuse the sandbox: `pnpm -F @holotype/sandboxes gen react-vite@10.6 --overlay faults --build storybook-static` gives the throwing, hanging and play-failing stories its e2e tests need, without adding stories to `fixtures/ds-react`.
